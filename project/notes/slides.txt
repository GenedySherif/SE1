SE I – 01a: Einführung und Motivation
SE I, WS2026/27, TZi, 1-12
Trend im Software Engineering: Continuous Delivery
 	Viele unabhängige Branches mit zeitgleichen Änderungen am
gemeinsamen Quellcode können Konflikte verursachen. Idee von
Continuous Integration ist es, mehrere Änderungen in einem
gemeinsamen Repository ständig zusammenzuführen. Damit soll ein
potenziell hoher merge-Aufwand bei Konflikten verhindert werden
 	Continuous Delivery ist eine Erweiterung zu Continuous Integration,
wobei zusätzlich nach erfolgreichem Test eine freigegebene Version
in ein Repository hochgeladen und von dort aus zur Auslieferung an
eine Produktivumgebung bereitgestellt werden kann
 	Beim Continuous Delivery können manuelle Freigabeprozesse sehr
aufwändig sein und den Lieferprozess verlangsamen. Um dies zu
vermeiden, kann beim Continuous Deployment auch noch eine
automatische Freigabe vom Repository zur Produktivumgebung
erfolgen. Dabei werden Tests mit sehr hoher Qualität vorausgesetzt

Was sind die Vorteile von Docker?
 	Der Vorteil von Containersoftware ist, dass Anwendungen ähnlich wie
bei virtuellen Maschinen vom Rest des System isoliert werden. Eine
JRE muss nicht lokal auf einem Rechner installiert sein
 	Jedoch enthält ein Container nicht eine komplette virtuelle Umgebung
mit eigenem Betriebssystem, sondern nur die notwendigsten
Ressourcen, um die Anwendung korrekt auszuführen
 	Dadurch sind Container einfacher, unabhängig von einem Host
(portabel), leichtgewichtiger und schneller als virtuelle Maschinen
 	Die Performance wird erhöht: es können mehr Anwendungen auf einer
gegebenen Hardware ausgeführt werden
 	Hohe Skalierbarkeit wird ermöglicht: Container können je nach Bedarf
auf einfache Weise, z.B. über Kubernetes, skaliert werden

Weitere Vorteile von Docker
 	Wie bei der Vererbung in Java kann ein Image auf einem Basis-Image
aufgebaut sein. Dieses Basis-Image kann wiederum ein Basis-Image

 	openjdk:24 verwendet
 	ubuntu:15.04 (Linux Betriebssytem)
 	nginx:latest (Proxy Server für HTTP, SMTP, … Protokolle)
 	Aktualität: Entwickler eines Teams laden über Docker Container das
gleiche Datenbankschema (volumes). Dadurch sind alle Änderungen
und der DB-Content für alle Entwickler beim Start immer aktuell

Nachteile von Docker
 	Persistenz: Docker Container sind zustandslos (stateless), d.h. bei
Beendigung der Ausführung sind alle Daten des Containers verloren
 	Über so genannte Docker Volumes (persistent, mounted) können zu
einem zustandslosen Container auch Daten dauerhaft gespeichert
(persistiert) werden
 	Greifen aber mehrere Docker Container gleichzeitig auf die gleichen
Volumes zu, dann wird die Einhaltung der Bedingungen für ACID-
Transaktionen zu einer großen Herausforderung
 	Docker Container haben daher ihre Stärken im Bereich von lesenden
Transaktionen, aber Schwächen bei schreibenden Transaktionen

Ausgangssituation
Ein Hotel bietet über eine Webanwendung die Registrierung eines Kunden sowie mögliche
Hotelbuchungen von Einzel- und Doppelzimmer an. Ein Kunde kann für weitere Personen,
die ihn begleiten, Buchungen in seine Hotelbuchung mitaufnehmen.
Zusätzlich ist es möglich, eine Hotelbuchung mit Dienstleistungen wie Buchung eines oder
mehrerer Mietwagen, Buchungen für Wellness-Angebote zu einem Wunschtermin und die
Ausgabe einer City Card für einen Tag zu ergänzen.
Restriktionen:
• 	Ein Kunde muss bei Erfassung einer Hotelbuchung registriert sein. Ein Kunde muss
genau eine Adresse haben, eine Adresse kann auch für mehrere Kunden gültig sein
• 	Buchungen nur von Dienstleistungen ohne die Buchung von mindestens einem
Hotelzimmer können nicht durchgeführt werden
• 	Es ist daher auch nicht möglich, alle Buchungen von Hotelzimmern zu stornieren,
wenn noch Buchungen von Dienstleistungen vorliegen. Es muss dann die gesamte
Hotelbuchung storniert werden
Stammdaten:
Die Hotelzimmer und Dienstleistungen mit Angabe Standardpreis sowie die Kundendaten
müssen durch Erfassung als Stammdaten in einer Datenbank gespeichert werden, wobei jedes
einzelne Hotelzimmer sowie jede Dienstleistung eindeutig identifiziert werden kann (z.B. EZ-
101, DZ-201, Porsche 911-1, SPA-Besuch, Rückenmassage, City Card Nr. 1145, usw.).
Alle Stammdaten können geändert oder gelöscht werden. Vor einer Löschung müssen jedoch
Prüfungen auf noch vorhandene Verwendungen in Bewegungsdaten durchgeführt werden.
Bewegungsdaten:
Alle Einzelbuchungen sollen als Positionen der Hotelbuchung hinzugefügt und ebenfalls in
einer Datenbank gespeichert werden, also z.B.:
Hotelbuchung 4711 zum Kunden 0815 mit Erfassungsdatum und Buchungszeitraum enthält:
HZ-Position 001: Einzelzimmer EZ-100
HZ-Position 002: Doppelzimmer DZ-200
DL-Position 001: SPA-Besuch mit Datum
DL-Position 002: SPA-Besuch mit Datum
DL-Position 003: City Card mit Tagesdatum

Derzeitige und zukünftige Architektur (Ist-Zustand und Soll-Zustand)
Die zugrundeliegende Architektur besteht derzeit aus einem Monolithen, der auf einer
klassischen 3-Schichten-Architektur (Datenebene, Anwendungsebene, Präsentationsebene)
und einem Client/Server-Modell basiert. Aufgrund der saisonal stark schwankenden Anzahl
an Hotelbuchungen und der dadurch sehr unterschiedlichen Auslastung des Servers soll eine
moderne Architektur der Webanwendung entwickelt werden, die innovative Technologien
verwendet. Die Verteilung der Anfragelast soll über eine skalierbare Plattform erfolgen.
Die Abteilung IT-Strategie beobachtet eine zunehmende Migration von Webanwendungen zu
einer komponentenorientierten Architektur, die sogenannte Microservices auf Basis von
Domain Driven Design (DDD) entwickelt. Diese vertikalen und horizontalen Microservices
werden als Docker Images implementiert und als Docker Container ausgeführt.
Um eine Skalierbarkeit der notwendigen Docker Container zu ermöglichen, wird bei IT-
Unternehmen sehr häufig eine Kubernetes Plattform verwendet, über die ein sogenanntes
Deployment der entsprechenden Docker Images durchgeführt werden kann. Dadurch ist es
auch möglich, die Anwendung in eine Private Cloud auszulagern.
Das Unternehmen entschließt sich daraufhin, ebenfalls diese Migration durchzuführen.
Es soll zunächst ein Pflichtenheft erstellt werden, das die Anforderungen an die Migration des
Monolithen zur komponenten- und serviceorientierten Architektur dokumentiert.

Aktivität: Aufwandsschätzung – Object-Point-Methode
 	Die Object-Point-Methode wurde 1994 von H. Sneed entwickelt und
verwendet die von R. D. Banker 1991 erfundenen Object Points
 	Object Points sind nicht zu verwechseln mit Objekten einer Klasse
 	Object Points werden unter Berücksichtigung von Vererbung und von
Wiederverwendung berechnet aus:
 	Class Points, die über die Summe der Methoden, Basisattribute
und Referenzen von Klassen berechnet werden
 	Message Points, die aus der Anzahl der Nachrichtenparameter
sowie unter Betrachtung des Integrationsaufwands und der
relativen Komplexität der Nachrichten berechnet werden
 	Process Points, die den Aufwand für Batch-, Dialog-, System-
und Echtzeitprozesse mit unterschiedlicher Gewichtung und
unter Betrachtung der Komplexität bewerten

SE I – 02: Konzeption und Planung
SE I, WS2026/27, TZi, 3-37
Aktivität: Aufwandsschätzung – Object-Point-Methode
 	Zunächst erfolgt die Berechnung der Summe der ungewichteten
Object Points (Class Points + Message Points + Process Points)
 	Anschließend erfolgt eine Justierung dieser Summe mit den zum IT-
Produkt definierten Qualitätsanforderungen, wie z.B. Sicherheit,
Zuverlässigkeit, Benutzbarkeit, Wartbarkeit, Effizienz und Portabilität
 	Jede Qualitätsanforderung wird mit 0 (minimaler Wert) oder mit 1
(Industriestandard) oder mit 2 (maximaler Wert) bewertet
 	Der Durchschnitt dieser Werte ergibt den Qualitätsfaktor QF
 	Die ungewichteten Object Points werden mit dem berechneten
Qualitätsfaktor QF multipliziert:
Quality Adjusted Object Points = Object Points
∗ QF

Definition Anwendungsfall:
 Ein Anwendungsfall beschreibt anhand eines zusammenhängenden

 Ein Anwendungsfall wird häufig auch als Use Case bezeichnet

Assoziationen
 	modellieren Beziehungen zwischen Objekten gleichrangiger Klassen

Assoziationen

Assoziation – Aggregation
Aggregation
 	Sonderfall der Assoziation
 	liegt vor, wenn zwischen den Objekten der beteiligten Klassen (kurz:
den beteiligten Klassen) eine Rangordnung gilt, die sich durch »ist Teil
von« bzw. »besteht aus« beschreiben lässt
 	man spricht vom Ganzen und seinen Teilen
 	Die Objekte der Aggregation bilden einen gerichteten azyklischen
Graphen:
 	wenn B Teil von A ist, dann darf A nicht Teil von B sein
 	shared aggregation (weak ownership): ein Teilobjekt kann
mehreren Aggregatobjekten zugeordnet werden
 	Das Ganze handelt stellvertretend und übergreifend für seine
Einzelteile
 	Die aggregierten Teile können zu einem anderen oder zum gleichen
Zeitpunkt auch mit anderen Objekten geteilt werden

Assoziation – Komposition
Komposition
 	ist eine starke Form der Aggregation
 	beschreibt, wie sich etwas Ganzes aus Einzelteilen zusammensetzt
und diese kapselt
 	Zusätzlich muss gelten:
 	Jedes Objekt der Teilklasse kann nur Komponente eines einzigen
Objekts der Aggregatklasse sein, d.h. die aggregierten Teile
werden niemals mit anderen Objekten geteilt
 	die bei der Aggregatklasse angetragene Kardinalität darf daher
nicht größer als eins sein (unshared aggregation, strong
ownership)

Assoziation – Komposition
Komposition (Forts.)
 	Die dynamische Semantik des Ganzen gilt auch für seine Teile
(propagation semantics)
 	wird beispielsweise das Ganze kopiert, so werden auch seine Teile
kopiert (d.h., es werden keine Referenzen auf Teile erzeugt)
 	Die Lebenszeit der Teile ist denen des Ganzen untergeordnet, d.h.
wird das Ganze gelöscht, dann werden automatisch auch seine Teile
gelöscht (they live and die with it)
 	"Existenzabhängiges" Teil
 	die Teile sind quasi miteinander verschmolzen
 	Beispiel: Haustreppe, wird mit dem Haus zusammen abgerissen

Vererbung (generalization) Unterklassen »unsichtbar«
 	Jede Klasse »kennt« nur ihre eigenen Attribute, Operationen und

 	außerhalb der Klasse nicht sichtbar (private)
(in der UML: - ), auch nicht für Unterklassen
 	für alle Unterklassen sichtbar (protected)
(in der UML: # )
 	für alle anderen Klassen sichtbar, d.h. öffentlich (public) (in der
UML: + )

 	SysML wurde von der OMG im September 2001 zur Analyse und

Was ist Docker?
 	Docker ist eine seit 2013 frei verfügbare Software, die es Nutzern
ermöglicht, Software isoliert, portabel und skalierbar auszuführen
 	Docker dient der Isolierung von Anwendungen, der Container-
virtualisierung und der Vereinfachung der Anwendungsbereitstellung
 	Docker ist zum Industriestandard von Containersoftware geworden
 	Beispiele für Anwendungen mit Docker sind:
 	Aktuelle Tagesnachrichten abfragen
 	Import eines Datenbankschemas (z.B. Maria DB oder MySQL DB)
 	Eine Webseite zur Administration einer Datenbank verwenden
 	Aktien-, Währungs-, Wertpapier- oder Rohölkurse abfragen
 	Bestellungen oder Buchungen durchführen
 	Verschiedene Cloud-Dienste zur Verfügung stellen

Was sind die Vorteile von Docker?
 	Der Vorteil von Containersoftware ist, dass Anwendungen ähnlich wie
bei virtuellen Maschinen vom Rest des System isoliert werden. Eine
JRE muss nicht lokal auf einem Rechner installiert sein
 	Jedoch enthält ein Container nicht eine komplette virtuelle Umgebung
mit eigenem Betriebssystem, sondern nur die notwendigsten
Ressourcen, um die Anwendung korrekt auszuführen
 	Dadurch sind Container einfacher, unabhängig von einem Host
(portabel), leichtgewichtiger und schneller als virtuelle Maschinen
 	Die Performance wird erhöht: es können mehr Anwendungen auf einer
gegebenen Hardware ausgeführt werden
 	Hohe Skalierbarkeit wird ermöglicht: Container können je nach Bedarf
auf einfache Weise, z.B. über Kubernetes, skaliert werden

Docker Komponenten
 	Das Dockerfile ist ein Skript, das alle Befehle für die Erstellung eines
Docker Images ausführt
 	Das Docker Image enthält alle benötigten Komponenten, wie
Laufzeitumgebung (z.B. JDK) oder Libraries sowie ein schlankes Unix
Betriebssystem (z.B. Ubuntu). Es ist zu allen Systemen portabel, auf
denen eine Docker Engine installiert ist
 	Zu einem Docker Image können beliebig viele Docker Container
erzeugt und ausgeführt werden. In einem Docker Container ist daher
alles enthalten, was zur Ausführung einer Anwendung notwendig ist.
Alle Container eines Images haben immer den gleichen Inhalt
 	Fazit: Nahezu unabhängig vom Betriebssystem und einer Hardware
können Docker Container virtuell und in der Cloud ausgeführt werden

Weitere Vorteile von Docker
 	Wie bei der Vererbung in Java kann ein Image auf einem Basis-Image
aufgebaut sein. Dieses Basis-Image kann wiederum ein Basis-Image
verwenden, so dass jeweils immer nur eine spezifische Information in
einem Dockerfile definiert werden muss
 	Beispielsweise muss im Dockerfile nicht Java JDK 24 explizit
angegeben werden, sondern dies kann über ein Basis-Image (Befehl
FROM) erfolgen. Beispiele für Basis-Images sind:
 	openjdk:24 verwendet
 	ubuntu:15.04 (Linux Betriebssytem)
 	nginx:latest (Proxy Server für HTTP, SMTP, … Protokolle)
 	Aktualität: Entwickler eines Teams laden über Docker Container das
gleiche Datenbankschema (volumes). Dadurch sind alle Änderungen
und der DB-Content für alle Entwickler beim Start immer aktuell

SE I, WS2026/27, Docker, 1-8
Nachteile von Docker
 	Persistenz: Docker Container sind zustandslos (stateless), d.h. bei
Beendigung der Ausführung sind alle Daten des Containers verloren
 	Über so genannte Docker Volumes (persistent, mounted) können zu
einem zustandslosen Container auch Daten dauerhaft gespeichert
(persistiert) werden
 	Greifen aber mehrere Docker Container gleichzeitig auf die gleichen
Volumes zu, dann wird die Einhaltung der Bedingungen für ACID-
Transaktionen zu einer großen Herausforderung
 	Docker Container haben daher ihre Stärken im Bereich von lesenden
Transaktionen, aber Schwächen bei schreibenden Transaktionen

Docker Registry und Docker Repository
 	Docker Images werden in einem Docker Repository gespeichert.
Dadurch ist auch eine Versionsverwaltung (z.B. über Git) möglich
 	Docker Repositorys und Dockerfiles können in einem öffentlichen oder
in einer privaten Registry für Nutzer zur Verfügung gestellt werden
 	Die Docker Standard Registry ist Docker Hub. Alle Docker Registry
Befehle (pull, push) beziehen sich zunächst auf Docker Hub
 	Weitere Docker Registrys sind beispielsweise GitHub oder Bitbucket.
Hier müssen für einen pull bzw. für einen push zusätzlich Pfadnamen
oder Adressen bzw. Befehle angegeben werden, z.B. git push origin
master für GitHub

 	Die manuelle Eingabe der Befehle für Docker und Docker Compose ist

 	Expose daemon on tcp://localhost:2375 without TLS

Erzeugung, Ausführung und Löschen eines Containers zu einem Docker Image
Es können beliebig viele Container zu einem Image erzeugt werden. Ein bestimmter
Container kann auch gestoppt und wieder gestartet werden.
6. Führen Sie folgenden Befehl zur Erzeugung eines Containers aus:
docker run --name hlnode docbuc/printheadlines:node
Über den Parameter --name wird hier eine Bezeichnung (hier: hlnode) für den
Container vergeben
7. Lassen Sie sich das Ergebnis in der PowerShell und in Docker Desktop anzeigen:
docker ps -a
8. Stoppen Sie den Container über:
docker stop hlnode
und lassen Sie sich den Inhalt und die Eigenschaften des Docker Containers in der
PowerShell anzeigen über:
docker inspect hlnode
Um den Container wieder zu starten und die Ausgabe aktualisiert anzuzeigen,
geben Sie ein:
docker start hlnode -a
Für jede weitere aktualisierte Ausgabe, geben Sie wiederum ein:
docker start hlnode -a
9. Löschen Sie schließlich den Container über:
docker rm --force hlnode
Lassen Sie sich das Ergebnis in der PowerShell und in Docker Desktop anzeigen:
docker ps -a
Optional:
Sie können die Übung analog für andere Programmiersprachen aus der ZIP-Datei bzw. im
GitHub-Verzeichnis durchführen.

Übung 3 (Docker Compose)
Aufgabenstellung
Docker Container sind zunächst einmal stateless (zustandslos), da ihre Daten nach dem Löschen des
Containers wieder verloren gehen. Um dies zu verhindern werden so genannte Volumes bzw. Bind
Mounts verwendet, die Daten auf einem Speicherträger auch nach dem Löschen eines Containers
persistieren können. Dadurch kann ein Docker Container auch die Eigenschaft stateful erhalten.
In dieser Übung soll ein Docker Container einen Datenbank Container über eine graphische
Oberfläche administrieren.
Die beiden Container kommunizieren dabei miteinander über ein Netzwerk.
Es 	wird 	ein 	Docker 	Image 	für 	eine 	MySQL-Datenbank 	sowie 	ein 	Docker 	Image 	für 	die
Administration dieser Datenbank verwendet.
Das Beispiel ist angelehnt an und leicht modifiziert:
(ÖgK2020) Öggi, B., Kofler, M.: Docker – Das Praxisbuch für Entwickler und DevOps-Teams.

# Datei: docker-compose.yml
# MySQL mit der Datenbank hotel einrichten
version: '3.1'
services:
mysql:
image: mysql
restart: always
environment:
MYSQL_ROOT_PASSWORD: geheim
MYSQL_DATABASE: hotel
volumes:
- ./db:/var/lib/mysql
- ./init:/docker-entrypoint-initdb.d

- "13306:3306"
phpAdmin:
image: phpmyadmin
environment:
PMA_HOST: mysql
ports:
- "8080:80"
3. 	Betrachten Sie den Inhalt dieser Datei. Es wurde den beiden Services mysql und phpAdmin
jeweils ein Docker Image zugeordnet. Diese Images werden aus Docker Hub importiert.
Über die Umgebungsvariable PMA_HOST findet der zweite Service den ersten Service
mysql. Weitere Umgebungsvariablen werden für das Passwort und für den Namen der
Datenbank angegeben. Das Netzwerk (siehe Abschnitt 4), über das die Docker Container
über Ports kommunizieren können, wird automatisch angelegt.
Weiterhin werden zwei Volume-Mappings für den Container angelegt, so dass Content
sowohl aus dem Datenbank Container gelesen und abgespeichert werden kann, als auch
Content in den Datenbank Container importiert werden kann:
- 	./db:/var/lib/mysql
- 	./init:/docker-entrypoint-initdb.d
Ein MariaDB Container speichert alle Datenbankdateien in /var/lib/mysql relativ zum
Verzeichnisbaum 	des 	Docker 	Containers 	(ÖgK2020). 	Zur 	Synchronisierung 	und 	zur
Speicherung dieser Dateien wird über dieses Mapping ein Volume-Verzeichnis ./db in
Ihrem Arbeitsverzeichnis bei der allerersten Ausführung von Docker Compose angelegt. Bei
erneuter Ausführung werden dann die Inhalte aus ./db in den Container nach Verzeichnis
/var/lib/mysql exportiert (natürlich nur falls dort etwas vorhanden ist).
Das Initialisierungs-Skript wertet das Verzeichnis /docker-entrypoint-initdb.d aus.
Alle dort befindlichen Skripte werden ausgeführt; alle dort befindlichen SQL-Dateien
werden in die durch MYSQL_DATABASE bezeichnete Datenbank importiert (ÖgK2020).
Wenn sich also vor Erzeugung des Containers in Ihrem Volume-Verzeichnis ./init z.B.
eine SQL-Datei befindet, so wird diese in das Container Volume bei Erzeugung des
Containers importiert. Dies setzt jedoch voraus, dass das Volume-Verzeichnis ./db leer ist.
